# M1：文档解析讲解稿

## 这个模块解决什么问题

M1 把 PDF 或 DOCX 变成后续大模型能够读取的统一文本对象。它只负责可靠地
“打开和读出”，暂时不判断论文研究了什么，也不调用大模型。

- 输入：一个本地 PDF 或 DOCX 文件路径。
- 处理：逐页或逐段读取文字，保留页级文本，整理基础元数据。
- 输出：`ParsedDoc`，其中包含文件名、格式、页数、全文、逐页文本和元数据。

同时，M1 用 `PaperRecord` 固定了全项目的 11 个目标字段。后续大模型、数据库、
接口和评测都复用同一份定义，避免每个模块对字段的理解不一致。

## 数据流

```text
PDF / DOCX 路径
      ↓
parse_document 判断后缀和文件状态
      ↓
pdfplumber 逐页读取 / python-docx 逐块读取
      ↓
ParsedDoc（全文、页数、逐页文本、元数据）
      ↓
M2～M3 截断文本并交给大模型抽取 PaperRecord
```

## 主要文件

### `app/models.py`

定义两个 Pydantic 数据模型：

- `ParsedDoc`：解析器的标准输出。
- `PaperRecord`：最终要抽取的 11 个字段。

`PaperRecord` 包含标题、作者、年份、发表平台、文档类型、研究问题、方法名称、
数据集、主要结果、局限性和摘要总结。年份限制在 1950～2030，研究问题最多
200 字，摘要总结最多 400 字，能尽早拦住明显不合理的数据。

### `app/parser.py`

提供统一入口 `parse_document(path)`：

- `.pdf` 使用 `pdfplumber` 逐页提取。
- `.docx` 使用 `python-docx` 按正文段落和表格顺序提取。
- 其他后缀直接报告“不支持的格式”。
- 加密、损坏和疑似扫描件分别产生容易理解的异常。

DOCX 文件没有像 PDF 那样稳定的物理页信息，同一份文档换字体或打印机后页数
可能变化，所以本项目把整个 DOCX 记作一个“逻辑页”，不伪造不可靠页码。

### `scripts/inspect_documents.py`

这是 M1 的独立运行入口。默认读取 `data/inbox` 内全部 PDF 和 DOCX，也支持
在命令行传入指定路径。每篇输出页数、字符数和前 500 字，方便肉眼验收。

### `tests/test_models.py` 与 `tests/test_parser.py`

测试覆盖 11 字段校验、正常 DOCX、缺失文件、不支持格式、扫描件、加密 PDF、
损坏 PDF 和智能截断。测试中的假文件放在 pytest 临时目录，运行结束后不污染
项目；项目固定使用 `.pytest-tmp`，避免 Windows 不同执行身份共用系统临时目录
时发生权限冲突。

## 关键 Python 语法和库

### `Path`

```python
path = Path("data/inbox/paper.pdf")
```

`Path` 是标准库的路径对象，比手工拼接反斜杠更安全。`path.exists()` 检查文件
是否存在，`path.suffix.lower()` 得到小写扩展名。

### 类型提示

```python
def parse_document(path: Path) -> ParsedDoc:
```

它与 Java 方法签名的作用相近，告诉阅读者输入应是 `Path`，返回值应是
`ParsedDoc`。Python 默认不会像 Java 编译器那样强制检查，Pydantic 会在模型
创建时补上运行时校验。

### 类、继承和枚举

```python
class EncryptedPDFError(DocumentParserError):
    pass
```

这里定义了“加密 PDF”这一具体异常，它继承通用解析异常。调用方既能统一捕获
`DocumentParserError`，也能针对某种错误单独处理。`DocumentType` 使用枚举，
把文档类型限制为约定好的几个值，作用类似 Java `enum`。

### `try / except / raise`

`try` 包住可能失败的文件读取；`except` 把第三方库的底层错误转换为面向用户的
项目异常；`raise ... from exc` 同时保留原始原因，方便开发时排查。

### `with` 上下文管理器

```python
with path.open("rb") as file_stream:
    with pdfplumber.open(file_stream) as pdf:
        ...
```

`with` 类似 Java 的 try-with-resources。无论成功还是报错，文件都会关闭，避免
Windows 因文件句柄未释放而无法移动或删除论文。

### Pydantic

`BaseModel` 描述结构，`Field` 描述长度和数值边界，`field_validator` 在保存前
清洗字符串。这样错误数据不会悄悄流入数据库。它不是数据库 ORM，只是数据
结构与校验工具。

### pdfplumber 与 python-docx

`pdfplumber` 读取 PDF 的文字层和页面信息；`python-docx` 读取 Word 文档中的
段落与表格。二者都不会做 OCR，因此扫描图片型 PDF 会被字符数阈值识别并提示。
这符合本项目只处理电子版论文的范围。

### 智能截断

`smart_truncate(text, max_chars)` 在文本过长时保留前 70% 和后 30%，中间插入
清晰标记。论文标题、摘要和方法通常靠前，结论与局限通常靠后，两端保留比只取
开头更适合后续字段抽取。

## 面试官可能会问的问题

### 1. 为什么解析层不直接调用大模型？

参考答案：解析和信息抽取是两个不同职责。解析层只保证把不同文件统一成可靠
文本，便于独立测试、替换解析库和定位错误；大模型调用失败时也不会影响文件
是否能读。分层后批处理可以分别统计解析失败和抽取失败。

### 2. 怎么识别扫描版 PDF，为什么不直接上 OCR？

参考答案：电子版论文通常有足够的文字层。当前实现统计整篇提取字符数，少于
100 个字符就提示疑似扫描件。项目目标数据是电子版论文，加入 OCR 会显著增加
依赖、速度和识别误差，因此先明确拒绝；如果未来输入范围改变，再把 OCR 作为
独立适配器加入。

### 3. Pydantic 模型相比普通字典有什么价值？

参考答案：普通字典容易缺字段、拼错键名或混入错误类型。Pydantic 用一处 Schema
统一字段、类型和边界，创建对象时立即校验，并能被后续 FastAPI 自动复用为接口
文档。这样模型输出、数据库写入和接口响应遵循同一份契约。
