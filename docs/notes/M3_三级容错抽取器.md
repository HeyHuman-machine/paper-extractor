# M3：三级容错抽取器讲解稿

## 先记住一句话

M3 不负责“让模型永远正确”，而是负责：**识别错误、尽量修正、修不好也留下完整
诊断，并且绝不让一篇失败论文拖垮整个批次。**

这是项目最核心的工程能力。M1 能读文字，M2 能调用模型，但只有 M3 才把不稳定的
模型输出变成后续数据库、接口和批处理可以依赖的统一结果。

## 输入、处理和输出

- 输入：论文纯文本 `text: str`。
- 处理：智能截断、调用 LLM、提取 JSON、Pydantic 校验、错误反馈、修正重试。
- 输出：`ExtractionResult`。成功时包含 `PaperRecord`；失败时包含阶段、错误类型、
  错误信息和最后一次原始输出。

```text
论文文本
  ↓
智能截断（前 70% + 后 30%）
  ↓
DeepSeek 返回字符串
  ↓
L1：JSON 能否解析？ ──否──→ 记录 json_parse → 修正重试
  ↓ 是
L2：Pydantic 能否校验？──否──→ 记录 schema_validate → 修正重试
  ↓ 是
返回 PaperRecord

重试耗尽 → L3：返回 ExtractionResult(success=False)，不抛异常
```

## 两类错误必须分清

### JSON 语法错误

例如：

```text
这篇论文的信息如下：title=Demo, year=2024
```

它不是 JSON，程序连字段都读不出来，失败阶段记为 `json_parse`。

M3 的 `parse_json_object()` 还会兼容这些常见情况：

- 模型在 JSON 外加了解释；
- 返回 `````json`` 代码块；
- JSON 前后有多余文字。

程序会从第一个 `{` 开始尝试解析对象，而不是依赖简单的字符串截取。

### Schema 业务错误

下面是合法 JSON，但不是合法 `PaperRecord`：

```json
{
  "authors": ["Alice"],
  "year": 1949
}
```

它缺少 `title`、`problem`、`summary` 等必填字段，而且年份越界。失败阶段记为
`schema_validate`。M3 会把 Pydantic 的具体错误反馈给模型，而不是只说“答案错了”。

## 三级容错到底是哪三级

### L1：JSON 清洗与解析

先把模型正文从普通字符串转换为 Python 字典。解析失败时记录：

- `stage=json_parse`
- 异常类型和错误消息
- 本次原始模型输出
- token、耗时和网络层重试次数

如果还有机会，就把错误加入修正 Prompt，再调用一次模型。

### L2：Pydantic 业务校验

JSON 解析成功后，用唯一的 `PaperRecord` 检查：

- 11 个字段是否齐全；
- 字段类型是否正确；
- `doc_type` 是否是允许的枚举；
- 年份是否在 1950～2030；
- problem 和 summary 是否超长。

校验失败时记录 `stage=schema_validate`，把具体错误反馈给模型修正。

### L3：失败隔离

默认 `LLM_MAX_RETRIES=2`，代表首次调用后最多再修正两次，总计最多三次模型调用。
如果仍失败，抽取器不会继续抛异常，而是返回：

```python
ExtractionResult(
    success=False,
    failure=ExtractionFailure(...),
    attempts=[...],
)
```

M4 批处理拿到这种失败结果后，可以记录并继续下一篇论文。

## 为什么不直接 `raise` 异常

单篇工具遇到错误后抛异常并不奇怪，但批量处理 50 篇论文时，如果第 7 篇输出
不合法就让整个进程退出，前面结果可能无法保存，后面 43 篇也不会处理。

M3 把预期失败“数据化”：成功和失败都用 `ExtractionResult` 表达。调用者只需检查
`result.success`，这就是失败隔离。

## 主要数据模型

### `ExtractionAttempt`

记录每一次模型调用：第几次、失败阶段、原始输出、错误、token、耗时。它相当于
一次完整的诊断快照。

### `ExtractionFailure`

记录最后的失败结论：卡在哪一层、错误类型、简化后的错误消息、最后原始输出。

### `ExtractionResult`

统一成功和失败：

- `success`：是否成功；
- `record`：成功时的 11 字段记录；
- `failure`：失败时的诊断；
- `retry_count`：M3 字段修正次数；
- `total_tokens`：所有 M3 尝试累计 token；
- `total_latency_ms`：包括修正调用在内的总耗时；
- `attempts`：每次尝试的完整记录。

模型校验器保证成功时只能有 `record`，失败时只能有 `failure`，避免自相矛盾的数据。

## 两种重试不要混淆

项目存在两层重试：

| 层级 | 负责文件 | 触发原因 | 记录位置 |
|---|---|---|---|
| HTTP 重试 | `app/llm.py` | 超时、429、5xx | `transport_retry_count` |
| 字段修正重试 | `app/extractor.py` | JSON 或 Schema 错误 | `ExtractionResult.retry_count` |

例如一次 DeepSeek 请求内部遇到 429 后恢复，这是通信重试；模型返回缺少 title，
再带着校验错误重新问一次，这是业务修正重试。分开统计更容易诊断费用和质量问题。

## 修正 Prompt

`append_repair_message()` 会保留原始论文消息，并追加：

1. 模型上一次原始回答；
2. 失败阶段；
3. Pydantic 或 JSON 解析的具体错误；
4. 只输出完整 JSON、不得编造的要求。

返回的是一个新列表，不会在原列表上悄悄修改，方便保留初始请求和编写测试。

## 关键 Python 知识

### `Protocol`

`ChatClient` 只规定抽取器需要一个具有 `chat()` 方法的对象。真实运行传入
`LLMClient`，测试传入 `FakeLLMClient`。它类似 Java 的小型接口，但 Python 采用
结构化类型：只要方法形状符合就可以使用。

### `json.JSONDecoder().raw_decode()`

普通 `json.loads()` 要求整个字符串都是 JSON。`raw_decode()` 可以从某个 `{`
开始解析第一个完整对象，因此能容忍 JSON 前后的多余文字。

### Pydantic `ValidationError`

`PaperRecord.model_validate(data)` 会同时检查全部字段。失败时的 `ValidationError`
带有字段位置、错误类型和约束值，可以直接成为模型修正依据。

### 防御式边界

输入为空、API 调用失败、JSON 错误和 Schema 错误分别映射成不同 `stage`。错误消息
限制为最多 1500 字符，既保留诊断价值，也避免把超长错误再次塞进 Prompt。

## 测试为什么不花钱

`FakeLLMClient` 按顺序返回预设字符串。例如：

```text
第1次：I cannot produce JSON
第2次：合法的 11 字段 JSON
```

测试可以断言第二次收到的 Prompt 含有 `json_parse` 错误。另一个测试让第一次
JSON 缺少 `title`，再检查修正 Prompt 中是否含 `schema_validate` 和 `title`。

这些都是本地对象，不访问 DeepSeek，不读取 `.env`，也不产生 token 费用。

## 面试官可能会问的问题

### 1. 为什么要把 JSON 解析和 Schema 校验分成两层？

参考答案：两者错误性质不同。JSON 解析解决语法问题，Schema 校验解决字段、类型和
业务约束问题。分层后可以给模型更精确的修正提示，也能统计到底是格式稳定性差，
还是字段质量差。

### 2. 为什么重试耗尽后不抛异常？

参考答案：项目面向批量论文。单篇模型输出失败属于预期业务失败，应该作为数据
记录并继续下一篇；只有程序无法继续的非预期系统错误才适合向上抛出。这样可以
保证批次完整执行，并在失败表中保留诊断证据。

### 3. 如何证明重试逻辑真的执行了，而不是只写在代码里？

参考答案：测试注入按顺序返回错误和正确内容的假客户端，断言调用次数、每次
`stage`、累计 token，以及第二次 Prompt 中包含第一次的具体错误。这样不依赖真实
模型的随机性，也不会产生 API 费用。
