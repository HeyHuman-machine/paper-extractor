# M9：准确率评测

## 一句话理解

M9 给系统安排了一场“有标准答案的考试”：先由人根据原论文写出正确答案，再比较程序抽取结果，最后用数字说明系统到底有多准、三级容错到底有没有提升。

## 为什么不能直接看六篇结果说“效果不错”

表格看起来合理，只说明它通过了人的粗略观察。简历中如果写“准确率 90%”，必须回答：正确答案是谁标的、怎么比较、哪些字段算进总分、失败论文怎么算、能不能复现。M9 就是把这些问题固定成程序。

## 完整流程

```text
6 篇种子开发集 → 冻结标注口径
30 篇独立盲测论文
   ├─ 人工逐篇确认 11 字段 → ground_truth/evaluation
   ├─ 无内容修正重试运行一次 → no_retry.json
   └─ M3 三级容错运行一次 → with_retries.json
                         ↓
                    metrics.py
                         ↓
       report.md + report.json + field_scores.png
                         ↓
                   M8 评测页面
```

## 第一步：人工标准答案

正式盲测使用 `eval/prepare_labels.py --blank-from-dir ...`，它只根据 PDF 文件名建立空白模板，不调用 DeepSeek，也不复制旧预测。模板默认：

```json
"needs_review": true
```

这表示它还没有经过论文核对，不能当正确答案。必须打开论文逐字段填写，确认后改成：

```json
"needs_review": false
```

正式报告要求 30 篇独立盲测标注全部确认。脚本不会用本轮 DeepSeek 预测生成标准答案，因为那等于让考生先把答案写给阅卷人看。

## 第二步：公平运行两轮

两轮使用相同论文、相同模型、相同 Prompt、温度 0 和相同网络重试：

- 基线：`max_repair_retries=0`，模型回答不合格时不做内容修正。
- 完整方案：`max_repair_retries=2`，允许 M3 根据 JSON/Pydantic 错误修正两次。

只改变 M3 内容修正次数，才能把差异归因于三级容错。`LLM_MAX_RETRIES` 仍负责网络超时、429 和 5xx，不属于本次自变量。

## 第三步：字段指标

| 字段 | 规则 | 为什么 |
|---|---|---|
| `year`、`doc_type` | 精确匹配 Accuracy | 只有一个明确值 |
| `title`、`method_name`、`venue` | 小写、去标点空格后，相似度 ≥ 0.9 | 容忍格式和缩写差异 |
| `authors`、`experimental_conditions`、`main_results` | 集合 Precision / Recall / F1 | 既关心多写，也关心漏写 |
| `problem`、`limitations`、`summary` | 人工评审，不进自动总分 | 自由文本没有唯一表述，字符像不等于事实正确 |

一篇论文抽取失败时，它的 8 个自动字段都记 0 分。这样系统不能靠“只评成功样本”抬高成绩。

## 总分怎么来

8 个自动字段各自产生 0～1 分数，然后做等权宏平均：

```text
overall_auto_score = 8 个字段分数相加 ÷ 8
```

报告同时给出：

- 抽取成功率
- 每个字段的原始 Accuracy 或 F1
- 无重试与三级容错的绝对提升（百分点）
- 相对提升（百分比）

面试时优先说“提升了 X 个百分点”，不要把百分点和百分比混为一谈。

## 关键 Python 文件

- `eval/metrics.py`：纯函数计算指标，类似 Java 工具类。
- `eval/prepare_labels.py`：`argparse` 读取命令行参数并生成草稿。
- `eval/run_predictions.py`：同一批论文运行两种配置。
- `eval/import_claude_labels.py`：读取 Claude 分批输出的连续 JSON 数组，匹配本地 PDF 并整理为待确认的 M9 标注草稿。
- `eval/output/report.md`：30 篇盲测真实运行生成的可读报告；详细分数以该报告为准。
- `eval/run_development_validation.py`：仅用 6 篇开发集验证 Prompt 版本，不参与最终盲测成绩。

## V2：原子化抽取与可复核列表指标

V1 的 `experimental_conditions` 和 `main_results` 以整句集合比较。一边把“2 Gbaud、4 Gbaud、1 km、5 km”合在同一句，另一边拆成四条时，即使事实正确也会被判为不匹配。

V2 分两层解决该问题：

1. Prompt 要求模型把条件输出为 `字段名: 值`，结果输出为 `指标: 数值 | condition: 条件`，让每条只承载一个事实。
2. 评测端把旧答案与新输出都拆成数值+单位、调制格式、光纤类型和关键指标等原子事实，再计算集合 F1；科学计数法会统一，但错误数值仍会被扣分。

V2 只在 6 篇开发集上调试，开发集验证中所有 42 条条件都遵守 `字段: 值`，17 条结果都遵守 `| condition:`。最终是否提升，必须用同一份冻结的 30 篇盲测集重新运行后再与 V1 对比。

### V2 同集复测结论

在 30 篇冻结盲测集、相同原子事实集合 F1 下，V1 无内容修复轮为 **69.61%**，V2 为 **69.77%**，绝对提升 **+0.17 个百分点**。V2 实际对 7 篇论文触发了内容修复；若与同样允许两次修复的 V1 容错轮比较，则为 69.37% → 69.77%，提升 **+0.40 个百分点**。

提升不具备简历亮点价值，因此不能通过继续查看这 30 篇结果来反复调 Prompt。后续优化只能回到开发集进行，复测时应确保两个版本使用相同的 `--repair-retries` 值，隔离 Prompt 版本这一唯一变量。

## V3：低分字段定向优化（未通过开发集门槛）

V3 根据 V2 的字段诊断，尝试解决“方法名臆造、条件遗漏、结果只写 BER”三类问题：

1. 方法名只有作者在标题、摘要或方法中正式命名时才填写；普通技术描述应为 `null`。
2. 条件提示覆盖信号、链路、器件、算法/仿真四类事实；结果提示覆盖损耗、串扰、带宽、迭代、动态范围等量化指标。
3. 对超长论文，文本截断保留开头、实验/结果段落和结尾三段，而不是只留首尾。

验证使用同一份 6 篇冻结开发集、同一模型、温度 0 和相同的 2 次内容修复。结果为 **6/6 成功**，但总分 **78.17% → 78.02%（-0.15 个百分点）**；实验条件 **34.26% → 31.56%**，主要结果 **57.76% → 59.29%**，方法名保持 **33.33%**。因此 V3 **不进入 30 篇盲测**，也不作为默认版本。

其中一部分实验条件失分来自 V3 多抽取光载波、线宽、发射功率等信息：它们可能真实，但冻结答案未必将它们纳入“实验条件”，因而被 F1 计为额外项。不能通过事后改评分规则把它变成提升；下一轮改动前，必须先依据原论文重新定义并冻结标注口径。

## V4：章节证据片段抽取（未通过开发集门槛）

V4 尝试不再把全文机械截断，而是拼装“论文开头、方法命名、实验/仿真/结果、结尾”四类带来源标签的片段，再交给同一个模型抽取。它保留为可复查的实验路径，但不作为默认抽取方式。

在同一份 6 篇冻结开发集、同一模型、温度 0、相同 2 次内容修复下，V4 为 **6/6 成功**，总分 **78.17% → 74.86%（-3.31 个百分点）**：方法名 **33.33% → 16.67%**，实验条件 **34.26% → 24.09%**，主要结果仅 **57.76% → 58.16%**。因此没有调用 30 篇盲测。

根因不是“取证思想无效”，而是 PDF 解析后的章节标题不稳定：有些论文没有被规则识别到实验标题，导致证据包遗漏实验条件；第 4 篇条件字段甚至输出空数组。下一轮若继续，应改为**字段关键词 + 数值单位**检索窗口，例如围绕 `Gbaud`、`km`、`dBm`、`BER`、`FEC`、`Experiment` 等命中位置取证，而不是依赖章节标题。

## V5：关键词与数值单位取证（未通过开发集门槛）

V5 不再依赖章节标题，分别围绕条件证据（`Gbaud`、`km`、`dBm`、`THz`、`nm` 等）和结果证据（`BER`、`FEC`、`penalty`、`gain` 等）从全文提取窗口。6 篇开发集全部成功，但总分为 **76.59%**，低于 V2 的 **78.17%**（**-1.57 个百分点**），因此没有调用 30 篇盲测。

值得保留的发现是：V5 的主要结果从 **57.76% 提升到 65.09%（+7.32pp）**，证明“围绕结果关键词取证”有效；但方法名称从 **33.33% 降至 16.67%**、实验条件从 **34.26% 降至 31.01%**。下一轮不应整篇论文统一切到关键词取证，而应采用**字段级混合策略**：元数据/方法名仍用 V2 的全文首尾策略，实验条件仍用 V2，只有 `main_results` 使用 V5 的结果证据窗口，然后在 6 篇开发集验证。

## V6：字段级混合（通过开发集门槛）

V6 保留 V2 抽取的全部 11 个字段，再对每篇论文额外调用一次结果专用模型请求。该请求只允许返回 `{"main_results": [...]}`；若失败则自动回退到 V2 的原结果，绝不修改其他字段。

在 6 篇冻结开发集上，V6 **6/6 精修成功**。逐字段校验确认：6/6 论文的其余 10 个字段与 V2 完全相同；只有 `main_results` 被替换。主要结果由 **57.76% → 64.16%（+6.39pp）**，总分由 **78.17% → 78.97%（+0.80pp）**。这满足“开发集先提升”的门槛，但增益仍不大，进入 30 篇盲测前应由用户确认 API 成本。

### V6 冻结盲测复测结论

经用户授权后，V6 对 30 篇冻结盲测论文各进行一次结果专用精修，30/30 成功。程序逐项确认所有论文的其他 10 个字段与 V2 完全一致，比较只涉及 `main_results`。最终 V2 为 **69.77%**，V6 为 **69.75%**，变化 **-0.02 个百分点**；主要结果字段为 **27.08% → 26.88%（-0.19pp）**。

因此开发集的改善没有泛化到独立盲测集，V6 不作为默认抽取版本，也不能写成“准确率提升”。这个负结果仍然有价值：它说明单一 6 篇开发集不足以保证优化泛化，后续实验应扩大开发集或采用交叉验证，而不是继续在已查看的 30 篇盲测集上调参。

## 阶段 A：评测诊断（不改 Prompt，不重跑 API）

在开始下一轮改进前，先冻结 V2 的 30 篇预测并完成诊断。此阶段只读取既有的
`eval/predictions/v2-evaluation/predictions.json` 与已冻结标注；**不会调用 DeepSeek，
不会修改 `app/prompts.py` 或抽取逻辑。**

### A1：为什么不能把 AI 复核说成人工复核

计划书原本要求第二位人类标注者盲标 8 篇，才能得到“人类自一致性上限”。本次由
Codex 完成的是**独立 AI 复核**：复核时不打开原 `ground_truth/evaluation`，只根据论文
填写方法名称、实验条件和主要结果。因此它可提示标注口径是否不稳定，但不等于严格的
人类自一致性，不能把其分数写成“人类上限”。

复核 8 篇得到：方法名称 37.50%，实验条件原子事实 F1 56.00%，主要结果原子事实 F1
32.58%。尤其是主要结果的低一致性说明：同一论文中“哪些结果值得记、如何拆条”本身
存在很大选择空间。

### A2-A4：量化诊断结果

固定 V2 的 30 篇预测后：

| 字段 | Precision | Recall | F1 | 模型/标注平均条数比 |
|---|---:|---:|---:|---:|
| 实验条件 | 60.20% | 21.28% | 28.67% | 0.65 |
| 主要结果 | 55.00% | 19.48% | 27.08% | 0.38 |

这表示模型输出不是主要“乱编一大堆”（Precision 中等），而是比原标注少记了大量原子事实，
特别是主要结果。可它仍不能直接证明都是模型漏抽：如果人工把同一句拆成六条、模型只写
两条，同样会导致 Recall 低。

方法名称使用 0.90 模糊阈值时为 30.00%；阈值放宽到 0.60 才为 50.00%。因此方法名中
既有措辞/长短写法问题，也有“是否存在正式方法名”的标注口径问题，不能只靠粗暴降低阈值
宣布提分。30 篇中有 4 篇 `null → null`，这部分本来就是正确的无方法名判断。

### A5：先逐例归类，再决定 B 阶段

`eval/output/diagnosis/failure_cases.md` 已按三个低分字段各导出最多 15 条低分论文。
其中“失败归类”留空，填写时只选以下一项：

- 模型漏抽
- 模型错抽
- 措辞不同但等价
- 切分粒度不同
- 标注本身有歧义

只有统计完这些类别，才知道 B 阶段该修改评测规则、重标结构化答案，还是优化抽取。
这是避免“看见分低就改 Prompt”的关键控制点。

## B1：方法名称评分规则校准（不调用 API）

B1 不改 Prompt、不重新抽取论文，只用固定 V2 预测做两套规则的**平行评分**。原因是 A4
发现方法名称中有不少“主方法相同，但标注写得更长、模型写得更短”的情况；若沿用纯字符
0.90 阈值，会把这些表述差异误判为错误。

候选规则先保留所有旧版命中，再仅增加以下可复核处理：

1. 移除解释性括号、比较对象与末尾通用后缀（如 `method`、`scheme`、`receiver`）。
2. 仅允许“纯缩写 ↔ 全称首字母”互认，例如 `FASCD` 和 `Filter-Assisted Self-Coherent Detection`。
3. 在上述归一化后，方法名相似度阈值使用 0.75。

它明确**不**做中英文自由翻译，也不把复合方法漏答成单一部件（如只回答 `DRE`）判为正确。
抽查 6 个从错变对的论文原文后，剔除了“KK 与多种补偿方法共同比较”的过宽案例。

| 指标 | 旧规则 | B1 候选规则 | 变化 |
|---|---:|---:|---:|
| 方法名称 | 30.00% | 50.00% | +20.00 个百分点 |
| 8 字段自动宏平均 | 69.77% | 72.27% | +2.50 个百分点 |

> [!warning] 结论边界
> 这 +2.50 个百分点来自**评分规则校准**，不是模型或 Prompt 变得更准；并且 30 篇盲测集
> 已被查看。简历不能写成“模型准确率由 69.77% 提升到 72.27%”。能诚实表述的是：系统针对
> 方法名称设计了可复核的分层匹配规则，并保留旧规则报告作对照。

运行入口：

```powershell
.\.venv\Scripts\python.exe -m eval.run_method_rule_calibration
```

输出在 `eval/output/rule-calibration-b1/`：`rule_calibration.json` 是可机读对照，
`rule_calibration.md` 逐项列出由错变对的论文及命中规则。

## B2：结构化输出试点（准备完成，尚未调用 API）

### 为什么要独立试点

A3 显示：模型输出条目数 / 人工标注条目数，实验条件为 **0.65**，主要结果仅 **0.38**。
这说明即使模型说对了一部分事实，也会因为“人工拆成多条、模型合成少条”而在列表 F1 中
失分。B2 的目标不是直接提分，而是把“怎样拆条”从自由文本约定改成固定对象结构。

```text
旧版："fiber_length: 80 km"
B2 ：{"name": "fiber_length", "value": "80", "unit": "km"}

旧版："BER: 2.1e-3 | condition: 80 km SSMF"
B2 ：{"metric": "BER", "value": "2.1e-3", "unit": null, "condition": "80 km SSMF"}
```

### 新评测规则

同一结构化人工答案同时评估 V2 旧文本输出和 B2 新输出：

| 情况 | 得分 |
|---|---:|
| 指标/条件名、数值（允许 ±5%）和单位一致 | 1.0 |
| 仅指标/条件名一致，但数值、单位或结果条件不一致 | 0.5 |
| 名称不一致 | 0.0 |

这里的 0.5 代表“模型抓住了同一指标但没有把数值/条件答对”，不是放水；它使错误类型可见，
不会把数值错误伪装成满分。

## 面试官可能会问

### 1. 为什么不用 LLM-as-a-Judge 评价摘要？

因为它会引入另一个模型的偏好和不稳定性，且当前规格强调可解释、可复现。客观字段程序评分，自由文本人工抽查，更诚实。

### 2. 为什么用宏平均而不是把所有字段混在一起计数？

不同字段的数据结构不同。宏平均先让每个字段产生同等权重的 0～1 分，再平均，避免作者很多的论文让 authors 指标支配总分。

### 3. 怎样证明提升来自 M3 容错？

使用相同论文、模型、Prompt、温度和网络重试，唯一改变的是 `max_repair_retries`。因此两轮差异主要来自 JSON 清洗、Pydantic 错误反馈和内容修正重试。
