# M4：批量调度讲解稿

## 先记住一句话

M4 不改变单篇论文的解析和抽取算法，而是负责把 M1 与 M3 **批量组织起来**：
同时处理多份文件、持续报告进度，并把每份成功或失败完整收集到 `BatchResult`。

```text
多个文件
  ↓
ThreadPoolExecutor（默认 3 个工作线程）
  ├─ 文件 A：M1 解析 → M3 抽取 → 成功
  ├─ 文件 B：M1 解析失败       → 记录失败
  └─ 文件 C：M1 解析 → M3 失败 → 记录失败
  ↓
BatchResult：总数、成功数、失败数、token、耗时、逐文件明细
```

## 输入、处理与输出

- 输入：多个 PDF / DOCX 路径。
- 处理：线程池分发、M1 解析、M3 抽取、进度回调、失败隔离和结果汇总。
- 输出：`BatchResult`。

主入口：

```python
run_batch(files, on_progress) -> BatchResult
```

## 为什么使用线程池

这个项目的大量时间花在读取文件和等待 DeepSeek 网络响应，属于 I/O 密集型任务。
`ThreadPoolExecutor` 可以在一个任务等待时让其他任务继续，并且能直接复用现有同步的
M1–M3 接口。

没有选择 `asyncio`，因为现有解析器、`httpx.Client` 和抽取器都是同步接口。现在强行
改成异步会让 M1–M3 一起变化，学习和维护成本大于 M4 的收益。

## 并发数为什么可配置

默认读取 `.env` 中的 `BATCH_CONCURRENCY=3`：

- `3`：最多同时处理三份文件，是速度与 API 压力之间的折中。
- `1`：关闭并发，完全串行，适合 API 限流或调试。
- 更大：可能更快，也更容易触发 429、占用更多连接，不应盲目提高。

## 进度回调是什么

M4 只产生进度，不决定进度显示在哪里：

```python
on_progress(current, total, filename, status)
```

- 控制台可以把它打印成 `[03/10]`。
- FastAPI 将来可以把它写入任务状态。
- Streamlit 将来可以用它更新进度条。

这种设计让业务逻辑与界面解耦。回调在每份文件**完成**时触发，`status` 为
`success` 或 `failed`。

## 失败隔离

M4 把失败分成三类：

| 阶段 | 含义 | 例子 |
|---|---|---|
| `parse` | M1 的可预期文档错误 | 文件损坏、扫描件、加密 PDF |
| M3 原阶段 | 抽取器已经结构化的失败 | `api_error`、`json_parse`、`schema_validate` |
| `pipeline` | M4 捕获的意外单文件异常 | 自定义解析器或未来代码出现 `RuntimeError` |

无论哪一类，当前文件都会得到 `BatchFileResult(success=False)`，其他线程继续。

## 为什么进度顺序和结果顺序可以不同

并发时，文件 B 可能比文件 A 先完成。进度回调按真实完成顺序发送，用户能及时看到
变化；最终 `BatchResult.files` 则恢复为上传顺序，让数据库和表格展示稳定。

## 三个新数据模型

### `BatchProgressStatus`

限制进度状态为 `success` 或 `failed`，避免各个界面随意拼写。

### `BatchFileResult`

保存文件路径、文件名、成功状态、`PaperRecord` 或 `ExtractionFailure`、重试次数、
token、耗时和 M3 尝试记录。

### `BatchResult`

保存批次总数、成功数、失败数、总 token、总耗时和逐文件明细。Pydantic 校验器会
检查汇总数字是否与明细一致，为 M5 入库提供稳定输入。

## 如何运行

不调用 DeepSeek 的 10 文件演示：

```powershell
.\.venv\Scripts\python.exe scripts\demo_m4_batch.py
```

也可以在 VS Code 的“运行和调试”中选择 `M4：10 文件批量演示（不花 API）`。

预期结果：8 成功、2 失败，其中一份模拟解析损坏，一份模拟 JSON 修正耗尽。

## 面试官可能会问

### 为什么用线程池，不用多进程？

任务主要等待文件和网络 I/O，不是大量 CPU 计算；线程更轻量，而且不需要在进程间
序列化 Pydantic 对象和客户端。若未来加入重型 OCR 或本地模型推理，才考虑进程池。

### 如何保证一篇失败不影响其他论文？

每份文件都在 `_process_one()` 边界内处理。解析异常、M3 失败结果和意外异常都会被
转换成当前文件的失败明细；主线程只收集 future 的最终结果，不因业务失败停止批次。

### 为什么不让 M4 直接打印进度？

打印会把业务层绑定到控制台。回调允许控制台、API 和 Streamlit 使用同一套 M4，
后续新增界面时无需修改调度逻辑。
